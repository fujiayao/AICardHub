# ADR-001：48 小时试点及协作调整

- 状态：已批准需求裁决与本地开发协作；交付先本地验收，部署另行进行
- 日期：2026-11-14
- 原依据：docs/工程框架方案.md、docs/开发执行计划.md、原40张任务卡。

## 背景

远程仓库尚空。原计划6–7周且要求一周灰度；当前希望1–2天开发测试上线。需要明确可控试点和全量一期不同，不能靠修改完成定义隐瞒未交付。

## 提议

1. 采用docs/48小时试点范围与发布门槛.md 所述最小闭环作为独立试点范围；未完成旧任务保留，不标全绿。
2. 保持既定FastAPI/MySQL8/Vue3技术栈。运行环境由已核验可用条件决定；若选原生Windows而非原文档WSL，需要统一等价PowerShell检查入口，不能混用三套目录与解释器。
3. 后端分业务与AI两个实现所有者；仅一位维护共享core、模型基类、Alembic、依赖和导出脚本。H5和后台可分开，根锁文件仍集成单写。
4. 独立QA由集成授权编写验收测试；实现者不可改验收断言。QA不自批标准，也不修改业务实现。
5. 产品知识优先项目自有、批准公开的版本化Markdown；现有知识库只做开发知识或经批准公开子集源，不整库复制、不向访客暴露MCP。
6. 不自动更改全局模型供应商、不共享管理员知识库凭据、不将私人测试库提交GitHub。
7. 48小时目标为候选版本/受控试点，一周灰度仍在后续真实时间验收。公开上线条件必须另核验。

## 需求冲突的拟议裁决

- 聊天中识别手机号只提示留资，明确同意并提交才创建线索；同步统一业务、UI、T09/T17与契约。
- 48h NFC只做固定员工短链测试，不承诺独立物理卡挂失换绑。
- 不凭未验证手机号归并客户/恢复历史；访客会话基于匿名token隔离；离职转交须授权及审计。
- 阶段质量门禁与功能阶段对应，最终试点范围全部检查仍须真实通过；旧全量标准不被删除。
