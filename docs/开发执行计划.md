## 2. 角色与分工

| 角色 | 工作目录（worktree） | 负责任务 | 可以改 | 不能改 |
|---|---|---|---|---|
| **你**（项目负责人） | — | T00、T53、T54；5 个把关点；批准 ADR | 一切 | — |
| **集成与质量智能体** | `shuke-ai-card/`（main 分支） | T01、T05、T08、T09、T41、T42、T50 | 根配置、scripts/、e2e/、tests/acceptance/、看板、审查意见、ADR 草稿 | 业务实现代码 |
| **后端智能体** | `shuke-ai-card-backend/` | T02、T06、T10–T23、T51、T52 | server/、deploy/、loadtest/ | apps/、tests/acceptance/、scripts/ |
| **前端智能体** | `shuke-ai-card-frontend/` | T03、T04、T07、T30–T38 | apps/h5/、apps/admin/ | server/、generated 目录（只能生成）、scripts/ |

设计原则：

- **三个角色改的目录互不重叠**，并行时几乎不会冲突。
- **集成智能体不写业务代码**，只审查、合并、写测试。这样审查者和实现者不是同一个，能拦住“自己审自己”的问题。
- **验收测试由集成智能体按方案写、你锁定**，实现智能体只能让测试通过。

## 3. 工具：Codex + magpie 各管什么

### 3.1 先说清楚 magpie 的作用

我查阅了 magpie 的官方文档：magpie 是一个**本地模型网关**，作用是给 Codex、Claude Code 等每个 Agent 选用哪个模型、在多个账号之间路由和故障转移，并统计用量。它**不负责给智能体分派任务，也不定义角色**。

所以本计划里的分工是：

| 事情 | 由谁负责 |
|---|---|
| 角色（是谁、能改哪里、怎么交付） | `AGENTS.md` + `.agents/roles/*.md` + 启动提示词 |
| 派任务、转达“已交付/已打回” | 你（在三个 Codex 会话之间转达），看板记录状态 |
| 每个角色用哪个模型、额度用完自动换 | magpie |
| 审查、合并 | 集成与质量智能体 |

### 3.2 推荐的 magpie 配置

magpie 的路由组支持按**项目文件夹**设置规则：Agent 在哪个文件夹里工作，就把请求优先发给指定模型。正好对应三个 worktree：

| 文件夹 | 推荐模型 | 原因 |
|---|---|---|
| `shuke-ai-card-backend` | 你手上最强的编码模型，推理强度高 | 后端逻辑最复杂（知识库、流式、并发） |
| `shuke-ai-card-frontend` | 强编码模型，推理强度中高 | 页面多但逻辑较简单，速度更重要 |
| `shuke-ai-card`（集成与质量） | **与实现者不同家族**的强模型 | 不同模型盲点不同，交叉审查更容易发现问题 |
| 所有文件夹的“压缩上下文” | 便宜快速的模型 | magpie 支持对压缩请求单独路由，省额度 |

配置要点：

- 在 magpie 中新建一个路由组（例如 `shuke`），给 Codex 选这个组；用 `folders=` 规则把三个文件夹分别指向上表模型；组内保留备用模型做故障转移，避免额度用完时智能体中途卡住。
- 仓库放在 WSL2 中时，Codex 报告的工作目录是 Linux 路径（如 `/home/你/work/shuke-ai-card-backend`），规则里写同样的路径。
- 改了 magpie 设置后，**已在运行的 Codex 会话不会生效**，要重开会话。
- **注意区分两个 API**：magpie 管的是“写代码的智能体”用的模型；名片产品自己调用的中转 API（GPT / DeepSeek）配置在仓库的 `deploy/.env`，两者不要混用同一个 Key。

具体命令与界面操作以 magpie 文档“快速上手 → 路由组 → 规则”为准：https://usemagpie.ai/docs/zh/start

### 3.3 Codex 使用要点

- **一个任务开一个新会话**。任务结束就关掉，下一个任务重开。长会话上下文会越来越脏，这是 vibe coding 质量下降的头号原因。
- Codex 会读取仓库根目录到当前目录路径上的 `AGENTS.md`；子目录的 `server/AGENTS.md`、`apps/h5/AGENTS.md` 只在该目录下工作时追加生效。
- 沙箱：用“可写工作目录 + 需要时请求批准”的模式。安装依赖、启动 Docker 需要网络和目录外权限，第一次会请求你批准；也可以在 Codex 配置中为工作目录写入模式打开网络访问（具体配置项以你安装的 Codex 版本文档为准）。
- 不要给智能体“全自动、无需批准”的权限去执行 `git push`、删除目录、修改 `~/.codex` 等操作。

## 4. 仓库与 worktree 布局

```text
~/work/
├── shuke-ai-card/              ← main 分支：集成与质量智能体在这里工作，也是合并的地方
├── shuke-ai-card-backend/      ← worktree：后端智能体，每个任务一个 feat/Txx-* 分支
└── shuke-ai-card-frontend/     ← worktree：前端智能体，每个任务一个 feat/Txx-* 分支
（三个目录共享同一个 Git 仓库，分支互相可见，不需要远程仓库）
```

初始化（T00）：

```bash
# 在 WSL2 中（Windows 的 D 盘在 WSL 里是 /mnt/d）
cd "/mnt/d/AIWork/智能名片/claude"
bash repo-init/bootstrap.sh ~/work/shuke-ai-card
```

- 仓库建议放在 WSL2 的家目录（`~/work`），不要放在 `/mnt/d` 下：Node 和 Python 在跨文件系统目录里会慢很多，文件监听也常出问题。
- 现在不需要 GitHub。本地 Git 从第一天就要用：它是回滚“智能体改坏了”的唯一保险。上线时再推到 GitHub（T54）。

## 5. 工作流程

### 5.1 一个任务的完整生命周期

```text
① 你：看板挑一个“开工条件已满足”的任务，状态改为 🔄，在对应 worktree 开新 Codex 会话，发启动提示词（§7）
② 智能体：从 main 开分支 feat/Txx-*，读任务卡与引用文档 → 开发 → 测试 → check.sh → 写交付报告 → 提交
③ 智能体回复“Txx 已交付”
④ 你：把这句话转给集成与质量智能体（它的会话可以常开，只做审查合并，或每次重开）
⑤ 集成智能体：审查
     通过 → 合并到 main → 重新生成契约 → check.sh → 看板 ✅
     不通过 → 写 tasks/reviews/Txx-rN.md → 看板 ↩️
⑥ 打回时：你在原 worktree 开新会话发“修复提示词”（§7），智能体 rebase 后逐条修复，回到 ③
⑦ 合并含数据库迁移或接口变更时：另外两个 worktree 执行 git rebase main（你转达一句即可）
```

### 5.2 每天的节奏（建议）

| 时间 | 你做什么 |
|---|---|
| 开始 | 看看板；给空闲的角色派下一个任务（每个角色同时只做一个任务） |
| 中途 | 转达“已交付”给集成智能体；回答智能体提出的问题；审批 ADR 草稿 |
| 结束 | 看当天合并了什么；有截图的任务快速对一下原型；有把关点的任务做审核 |

### 5.3 什么时候可以并行

- 阶段 0：T02（后端）与 T03、T04（前端）可以并行；T06、T07 必须按顺序（先后端后前端）。
- 阶段 1：G2（T10 契约）通过后，后端、前端、集成三条线完全并行。
- 前端任务的“开工条件”只看契约（T10）与前一个前端任务；“联调依赖”的后端任务没合并时先用 Mock。

### 5.4 契约变更

T10 之后接口字段冻结。任何角色想改字段：写 `docs/adr/NNNN-*.md` 草稿 → 停下 → 你批准 → 后端改 schema 并重新生成 → 集成智能体合并时在看板标注“接口变更” → 前端 rebase 后编译报错的地方就是要改的地方。

### 5.5 遇到问题怎么办

| 状况 | 处理 |
|---|---|
| 智能体说“需求不清楚” | 回答它，并把答案补进任务卡或写成 ADR，避免下次再问 |
| 同一问题连续修两次没修好 | 按规则它会停下报告；你判断是任务太大（拆卡）、方案有缺口（写 ADR），还是换个会话/模型重来 |
| 测试一直不过，智能体想改测试 | 不允许改验收测试；如果确认测试本身写错，让集成智能体修改测试并由你批准 |
| 合并冲突 | 生成文件冲突：直接重新运行 gen-api.sh；迁移冲突：后合并的分支 rebase 后重新生成迁移；业务代码冲突：说明目录划分被打破，查原因 |
| 改坏了、想回退 | 未合并：直接丢弃分支重开；已合并：集成智能体 `git revert` 该合并提交 |
| 模型额度用完、会话卡住 | magpie 路由组的备用模型会接上；仍卡住就关会话，新会话从任务卡和分支现状继续（任务卡 + 提交记录就是“记忆”） |
| 会话太长、开始犯低级错 | 立即提交当前进度，关掉会话，新会话发“继续任务”提示词 |

### 6.1 任务卡里写了什么

每张卡都包含：角色、开工条件、联调依赖、依据（方案章节与原型页面）、目标、允许修改的目录、不得修改的目录、接口（operation_id）、数据库变更、逐条验收标准、必须通过的命令、交付要求。智能体只需要“读卡 + 读卡里引用的章节”，不需要通读全部文档。

### 6.2 为什么要先做“全量接口契约”（T10）

如果每个后端任务各自定义接口，前端就得等后端一个个做完，三个智能体实际上是串行的。T10 一次把所有接口的字段定下来（函数体先返回 501），你审核一次，前端立刻能生成全部类型并用 Mock 开发，集成智能体也能据此先写验收测试。代价是你在 G2 要花 1–2 小时认真看一遍接口清单。

## 7. 启动提示词模板

把 `{}` 换成实际内容后直接粘贴到对应 worktree 的新 Codex 会话中。

**后端 / 前端：开始新任务**

```text
你是本项目的{后端智能体 / 前端智能体}。
请依次阅读：AGENTS.md、{server/AGENTS.md / apps/h5/AGENTS.md}、.agents/roles/{backend / frontend}.md、tasks/T{xx}.md，以及任务卡“依据”中列出的文档章节。
读完后先用 5 行以内复述：任务目标、允许修改的目录、验收标准条数、需要运行的检查命令。确认无误后开始执行。
不清楚的地方先问我，不要猜。完成后按规定写交付报告并回复交付信息。
```

**后端 / 前端：修复打回**

```text
你是本项目的{后端 / 前端}智能体。任务 T{xx} 被打回。
请执行 git rebase main，阅读 tasks/reviews/T{xx}-r{n}.md，逐条修复（不要做审查意见以外的改动），
在 tasks/reports/T{xx}.md 末尾追加“第 {n} 轮修复说明”（逐条对应），check.sh 通过后提交并回复。
```

**继续未完成的任务（新会话接手）**

```text
你是本项目的{角色}。任务 T{xx} 在之前的会话中未完成。
```

**集成与质量：审查**

```text
你是本项目的集成与质量智能体。请阅读 AGENTS.md 和 .agents/roles/integrator.md。
任务 T{xx} 已交付，分支 feat/T{xx}-{name}，报告 tasks/reports/T{xx}.md。
请按角色文件中的“审查与合并流程”执行：对照任务卡验收标准和审查清单逐条检查，运行 check.sh，
给出“通过并已合并”或“打回（附 tasks/reviews/T{xx}-r{n}.md）”的结论，并更新看板。
```

**集成与质量：执行自己的任务**

```text
你是本项目的集成与质量智能体。请依次阅读 AGENTS.md、.agents/roles/integrator.md、tasks/T{xx}.md 及其依据章节，
先复述目标、允许修改的目录和验收标准，确认后执行。完成后写报告 tasks/reports/T{xx}.md 并提交到 main。
```

## 8. 防跑偏的几道闸

| 闸 | 拦住什么 | 在哪里 |
|---|---|---|
| 任务卡“允许修改”目录 | 一次改太多、改别人的代码 | 每张任务卡；审查清单第 1 条 |
| 开工复述 | 没读懂任务就开干 | 启动提示词要求先复述 |
| scripts/check.sh | 类型错误、旧写法、手改生成文件、颜色字面量、残留 TODO、密钥 | 每次交付前；每次合并后 |
| 验收测试锁定 | 改测试迎合代码 | T09 编写、你签字锁定 |
| 交叉审查 | 实现者自审 | 集成智能体用不同家族模型 |
| 契约冻结 + ADR | 接口漂移、擅自改方案 | T10 / G2；§5.4 |
| 截图对照原型 | 页面越做越偏 | 每个前端任务的交付要求；T50 |
| 一任务一会话 | 上下文污染 | §3.3 |
| 本地 Git 分支 | 改坏无法回退 | 每个任务一个分支，合并用 --no-ff |
