> 版本：v1.0｜日期：2026-11-14｜状态：待确认
>
> 用途：确定“用什么技术、按什么结构、守什么规矩”来写代码，并作为多个 AI 智能体协作开发时的统一标准。
>
> **文档优先级**（多份文档说法不一致时按此裁决）：

> 2. 页面长什么样、交互和组件规格：以 `数科AI智能名片_UI设计规范.md` 和 `数科AI智能名片_H5原型.html` 为准；
> 3. 业务流程、数据模型、接口清单、知识库规则：以 `数科AI智能名片_业务流程与开发方案.md` 为准；

## 0. 结论速览

| 部分 | 选型 | 一句话理由 |
|---|---|---|
| 后端语言 | **Python 3.12** | 大模型调用、Markdown 知识库、PDF/Word 解析、海报生成都是 Python 生态最强项 |
| 后端框架 | **FastAPI** + Pydantic v2 + SQLAlchemy 2.0（异步）+ Alembic | 原生异步流式输出；自动生成 OpenAPI，前端据此生成类型，接口不会漂移 |
| 访客 H5 + 员工端 H5 | **vue3-vant-mobile**（Vue 3 + Vite + Vant 4 + Pinia + UnoCSS 的移动端工程模板） | 自带文件路由、请求封装、Mock、PWA、调试面板、移动端适配，和原型的 Vant 组件规格一一对应 |
| 管理后台 | **pure-admin-thin**（vue-pure-admin 的精简版，Vue 3 + Element Plus） | 单应用、轻量、带登录/布局/表格，不是 monorepo，智能体容易看懂 |
| 数据库 | MySQL 8（开发、测试、生产都用 MySQL，不用 SQLite） | 避免“本地能跑、线上报错”的方言差异 |
| 包管理 | 后端 **uv**，前端 **pnpm** | 都有锁文件，依赖版本可复现 |
| 部署 | Docker Compose：nginx + api + scheduler + mysql | 一台服务器、一条命令 |
| 前后端关系 | **分离开发、同一仓库、同一域名** | 接口是唯一的契约；同域无跨域问题 |

## 1. Python 还是 Java

你两种语言都会，所以只看项目本身。

### 1.1 本项目的工作量分布

| 工作 | 占后端工作量 | Python | Java |
|---|---|---|---|
| 大模型调用（流式、主备切换、tool calling） | 高 | 官方 `openai` SDK，最成熟；示例和资料最多 | Spring AI / LangChain4j 可用，但版本迭代快，资料少一截 |
| 知识库引擎（md 解析、frontmatter、Token 估算、按需加载） | 高 | `python-frontmatter`、`tiktoken` 现成 | 需要自己拼，Token 估算库少 |
| PDF / Word 转 md | 中 | `pymupdf`、`python-docx` 简单好用 | PDFBox / POI / Tika 可用，代码量更大 |
| 海报、二维码、vCard | 低 | Pillow、qrcode，几十行 | Java2D 可做，但调字体和排版更麻烦 |
| 常规增删改查（员工、名片、线索、消息） | 中 | FastAPI + SQLAlchemy 足够 | Spring Boot + MyBatis-Plus 很成熟，若依类脚手架可直接生成 |
| 管理后台的用户/权限 | 低（只有管理员和员工两种角色） | 自己写，约 1 天 | 若依自带，但权限体系远超需要 |

### 1.2 从 AI 智能体写代码的角度

| 维度 | Python | Java |
|---|---|---|
| 代码量 | 同样功能约为 Java 的一半，智能体一次能“看全”的代码更多 | 文件多、样板代码多，上下文更容易溢出 |
| 类型安全 | 动态语言，智能体容易写出“能跑但类型错”的代码 → **用 Pydantic + mypy 严格模式补上** | 编译期就能拦住大量错误，这是 Java 的真实优势 |
| 框架熟悉度 | FastAPI 是智能体最熟悉的 Python Web 框架之一 | Spring Boot 同样很熟 |
| 版本陷阱 | Pydantic v1→v2、SQLAlchemy 1.x→2.0 写法差异大，智能体常混用旧写法 → **本方案第 11 章列了禁用写法** | Spring Boot 2→3（javax→jakarta）同样有坑 |

### 1.3 结论

**选 Python**。决定性因素是本项目一半以上的难点在“大模型 + 知识库 + 文档处理”，这正是 Python 的主场；Java 的主要优势（编译期类型检查、若依式开箱后台）在本项目里分量不大，而且类型安全可以用 Pydantic + mypy 严格模式补到够用。

**什么情况下改选 Java**：数科有现成的 Java 运维体系（统一的 Spring Cloud 网关、监控、发布流水线），或者后续长期维护的人只会 Java。届时推荐 Spring Boot 3 + MyBatis-Plus + Spring AI + Apache Tika，前端方案不变。

## 2. Vue 3 工程框架选型

Vue 本身就是框架，你说的“带框架的”是指**工程化模板**：已经搭好路由、状态管理、请求封装、代码检查、Mock、打包配置的项目骨架。用模板的好处是智能体不用从零搭工程，也不会每个智能体搭出不一样的结构。

另外说明：Nuxt 这类“元框架”主要解决服务端渲染和搜索引擎收录，名片通过链接、NFC 打开，不需要被搜索引擎收录，所以不选。

### 2.1 访客 H5 + 员工端 H5：vue3-vant-mobile

仓库：https://github.com/easy-temps/vue3-vant-mobile （MIT 协议，2026-11 查阅时版本 3.16.0）

| 候选 | 结论 | 原因 |
|---|---|---|
| **vue3-vant-mobile** | ✅ 选用 | 技术栈与原型完全一致（Vant 4）；自带文件路由、axios 封装、Mock 服务、PWA（正好用于“添加到桌面”）、vConsole 真机调试、移动端尺寸适配；维护活跃，依赖较新 |
| vue3-h5-template 等老模板 | ❌ | 多年未大更新，依赖老旧 |
| uni-app / unibest | ❌ | 为多端（小程序/App）设计，一期只做 H5，引入会增加复杂度；二期小程序用 web-view 套壳即可 |
| Nuxt + Vant | ❌ | 不需要服务端渲染 |

模板自带的技术栈（2026-11 的 package.json）：Vue 3.5、Vite 8、Vant 4.10、Pinia 4、Vue Router 5（内置文件路由）、TypeScript 6、UnoCSS、axios、VueUse、ESLint（antfu 配置）、simple-git-hooks + lint-staged + commitlint。Node ≥ 22.23，pnpm 版本按模板 `packageManager` 字段。

**拿到模板后必须做的改造**（M1 骨架任务完成，见第 9 章）：

| 改造项 | 原因 |
|---|---|
| 删除 i18n（`vue-i18n`、`src/locales`、相关插件和自动导入） | 只有中文；留着会让智能体到处写 `t('xxx')` |
| 删除 echarts、sitemap 插件 | B2 的柱状图用 CSS 画即可；名片不需要站点地图 |
| `vite.config.ts` 代理：去掉把 `/api` 前缀剥掉的 `rewrite` | 后端路径本身就是 `/api/v1/...`，剥掉会导致开发环境 404 |
| `build.cssCodeSplit` 改为 `true` | 模板默认把所有 CSS 打成一个文件，访客页会加载员工端样式 |
| `src/utils/request.ts`：请求头改为 `Authorization: Bearer <token>`；超时改为 30 秒；按第 6.4 节统一错误处理 | 模板默认 `Access-Token` 头和 6 秒超时；文档导入、AI 润色会超过 6 秒 |
| PWA：只保留 manifest（名称、图标、主题色改为数科），**关闭 Service Worker 缓存** | Service Worker 缓存会让员工手机长期停留在旧版本，发版后看不到更新；“添加到桌面”只需要 manifest |
| 移动端适配插件（postcss-mobile-forever）：`viewportWidth` 设为 **390**，电脑上打开时最大显示宽度 480 并居中 | 与原型和 UI 规范的 390 设计宽度一致 |
| UnoCSS：主题色只映射 UI 规范里的 tokens；图标改用 `@iconify-json/lucide`（写法 `i-lucide-phone`） | UI 规范规定线性图标、颜色只用 tokens |
| 引入 `src/styles/tokens.css`（UI 规范 2.6 节原样复制）并映射 Vant 主题变量（UI 规范第 3 章） | 视觉统一 |
| 保留：Mock 服务（后端接口完成前用）、vConsole（仅开发和测试环境）、legacy 插件（兼容老安卓 WebView） | — |

### 2.2 管理后台：pure-admin-thin

仓库：https://github.com/pure-admin/pure-admin-thin （MIT 协议，2026-11 查阅时版本 6.2.0）

| 候选 | 结论 | 原因 |
|---|---|---|
| **pure-admin-thin** | ✅ 选用 | 精简版（不带一堆演示页面）、单应用结构、Element Plus、TypeScript；登录、布局、标签页、表格封装都有 |
| vue-vben-admin v5 | ❌ | turbo monorepo + 多套 UI 库变体，结构复杂，智能体容易改错包；对一个只有 10 个页面的后台过重 |
| RuoYi-Vue3（若依前端） | ❌ | 与若依后端的菜单/权限接口强绑定，换成 FastAPI 后要改大量适配 |
| 原生 Vue + Element Plus | ❌ | 你已明确要用带框架的模板 |

模板自带：Vue 3.5、Vite 7、Element Plus 2.11、Pinia 3、Vue Router 4、Tailwind CSS 4、TypeScript 5.9、ESLint + Prettier + Stylelint、husky。

**拿到模板后必须做的改造**：

| 改造项 | 原因 |
|---|---|
| 关闭“后端返回动态路由”（`getAsyncRoutes`），全部改为前端静态路由 | 模板默认从后端拉菜单；本项目只有管理员一种角色 |
| 关闭 refresh token 自动刷新逻辑；管理员 token 有效期 12 小时，过期重新登录 | 模板默认依赖 `/refresh-token` 接口，没必要为它加接口 |
| 在 `src/api/adapters/` 写一层适配：把本项目接口的返回结构转换成模板组件期望的结构 | 模板默认接口返回 `{ success, data }`，本项目接口直接返回数据（见 6.4），**后端不为模板改接口格式** |
| 删除模板自带的 mock 登录和示例页面 | 防止智能体照着示例写出与本项目无关的东西 |
| Markdown 编辑器用 `md-editor-v3` | 公司知识库在线编辑（C6） |

> 两个前端的 Pinia、Vue Router 大版本不同（H5 是 Pinia 4 / Router 5，后台是 Pinia 3 / Router 4），这是两个模板各自的选择，**两个前端保持完全独立**（各自的 package.json 和锁文件），不共享代码，也不建 pnpm workspace，避免版本互相干扰。

## 3. 后端框架

### 3.1 为什么是 FastAPI

| 候选 | 结论 | 原因 |
|---|---|---|
| **FastAPI** | ✅ 选用 | 原生 async，SSE 流式简单；用 Pydantic 定义请求和响应，**自动生成 OpenAPI**，前端据此生成类型；智能体非常熟悉 |
| Django + Django Ninja / DRF | ❌ | 自带后台和 ORM 是优点，但本项目后台已用 Vue；Django ORM 的异步支持仍不完整，流式对话和异步大模型调用写起来别扭 |
| Litestar | ❌ | 技术上不错，但生态和智能体熟悉度明显不如 FastAPI |
| RuoYi-Vue3-FastAPI（若依 FastAPI 版） | ❌（不作为基础） | 带完整的菜单/角色/字典/代码生成，但本项目只有两种角色，引入后 70% 是用不上的代码，而且强制依赖 Redis、绑定若依前端；智能体在大量无关代码里更容易改错地方 |

### 3.2 后端技术栈

| 用途 | 选型 | 说明 |
|---|---|---|
| Web 框架 | FastAPI | 版本迭代很快（2026-11 已到 0.162.x），**锁定精确版本**，升级单独做 |
| 数据校验 / 序列化 | Pydantic v2 + pydantic-settings | 只用 v2 写法（见 11.2） |
| ORM | SQLAlchemy 2.0（异步，`Mapped[]` 类型注解写法） | 不用 SQLModel：它把数据库模型和接口模型混在一起，智能体容易把内部字段暴露给接口 |
| 数据库驱动 | asyncmy | MySQL 异步驱动 |
| 迁移 | Alembic | 见 11.1 迁移规则 |
| ASGI 服务器 | uvicorn | 生产 2 个 worker |
| HTTP 客户端 | httpx（异步） | 禁止在异步代码里用 requests |
| 大模型 | `openai` 官方 SDK（`base_url` 指向中转 API） | **不引入 LangChain / LlamaIndex**：抽象层厚、版本变化快，本项目的需求用 SDK 直接写更清楚 |
| 知识库 | python-frontmatter、tiktoken、filelock | 文件读写加锁（多 worker） |
| 文档解析 | pymupdf、python-docx | 在线程池中执行（它们是同步库） |
| 图片 / 二维码 | Pillow、qrcode | 海报、名片二维码 |
| 鉴权 | PyJWT、bcrypt | — |
| 定时任务 | APScheduler **3.11.x** | 不要用 4.x（API 完全不同，智能体会混用）；只在独立的 scheduler 进程里运行 |
| 日志 | loguru | 统一格式，带请求 ID |
| 工具链 | uv、ruff（检查 + 格式化）、mypy（严格模式）、pytest、pytest-asyncio、pytest-cov | — |

> 版本策略：上表写明了大版本的地方必须遵守；其余库在 M1 骨架任务时用 `uv lock` 锁定当时最新稳定版，之后升级任何依赖都要单独提交、单独验证。

### 3.3 后端分层与模块

按**业务领域**分模块，每个模块内部再分层。这样多个智能体并行开发不同模块时，改的是不同目录，很少冲突。

```text
server/app/
├── main.py                  # 创建 FastAPI 应用、注册路由、中间件、异常处理（只做组装）
├── core/                    # 跨模块基础设施（只有架构负责人可以改）
│   ├── config.py            # pydantic-settings，所有配置项从环境变量读
│   ├── db.py                # 异步引擎、Session 工厂、Base
│   ├── security.py          # 密码哈希、JWT 签发与校验
│   ├── deps.py              # 依赖注入：get_db、get_current_staff、get_current_admin、get_visitor
│   ├── errors.py            # AppError + 错误码注册表 + 全局异常处理
│   ├── pagination.py        # 统一分页参数与返回结构
│   ├── ratelimit.py         # 限流
│   └── logging.py
├── modules/                 # 业务模块，每个模块结构相同
│   ├── auth/
│   ├── company/             # 企业信息、产品卡片
│   ├── template/            # AI 模板
│   ├── employee/
│   ├── card/                # 名片、分享（二维码/海报/vCard）
│   ├── assistant/           # AI 助手配置、润色、个人知识、纠错
│   ├── visitor/             # 访客、访问记录
│   ├── chat/                # 会话、消息、SSE、留资触发
│   ├── lead/
│   ├── notification/        # 站内信
│   ├── issue/               # 问题池
│   ├── nfc/
│   ├── stats/
│   └── settings/            # 模型、限额、回答规则
│       ├── router.py        # 只做：参数接收、调用 service、返回 schema。不写业务逻辑，不直接查库
│       ├── schemas.py       # Pydantic 请求/响应模型
│       ├── service.py       # 业务逻辑。不 import fastapi
│       ├── repo.py          # 数据库读写。所有“员工自己的数据”查询必须带 employee_id 参数
│       └── models.py        # SQLAlchemy 模型
├── kb/                      # 知识库引擎：纯 Python 包，不 import fastapi、不碰数据库会话
│   ├── store.py             # 文件读写、加锁、本地 Git 提交与回滚
│   ├── loader.py            # 扫描、frontmatter 解析与补全、索引
│   ├── prompt.py            # System Prompt 组装（方案 6.4 的固定顺序）
│   └── router.py            # route 模式：tool calling / 预路由 / 关键词兜底
├── integrations/            # 外部服务适配，方便测试替换
│   ├── llm/                 # LLMClient 接口 + OpenAICompatClient + FakeLLMClient（测试用）
│   └── storage/             # 文件存储接口 + 本地磁盘实现（以后可换对象存储）
├── jobs/                    # 定时任务：会话摘要、每日汇总、清理
├── scheduler.py             # 独立进程入口：python -m app.scheduler
└── export_openapi.py        # 不启动服务直接导出 openapi.json
```

依赖方向只允许：`router → service → repo → models`，`service → kb / integrations`。模块之间互相调用只能调对方的 `service`，不能直接用对方的 `repo` 或 `models`。

## 5. 前端结构与规则

### 5.1 apps/h5 目录

```text
apps/h5/src/
├── pages/                   # 文件路由（Vue Router 5 内置），目录即路由
│   ├── card/[code].vue      # A1 名片首页（A4 停用、A5 浮层在页面内按状态渲染）
│   ├── chat/[code].vue      # A2 对话页（A3 留资成功在页面内切换）
```

### 5.2 前端规则（两个前端通用，后台只要求前 6 条）

1. **页面与原型一一对应**：每个页面文件第一行注释写原型编号，如 `<!-- 原型: A1 名片首页 -->`；新增原型里没有的页面要先写 ADR。
2. **只有一个请求入口**：所有接口调用都用 `api/generated` 里生成的函数（通过 `api/client.ts` 发出）。禁止在页面里直接写 `axios` / `fetch` / URL 字符串。唯一例外是 SSE，只能用 `api/sse.ts`。
3. **只有一套 UI 库**：H5 只用 Vant + 本项目 `components/`；后台只用 Element Plus。禁止引入第二个 UI 库或图标库。
4. **类型严格**：`strict: true`，禁止 `any`（ESLint 报错级别）、禁止 `@ts-ignore`；接口数据类型只能来自 `api/generated`。
5. **单文件不超过 300 行**，超了就拆组件或 composable。
6. **提示用模板自带方式**：H5 用 `showToast` / `showDialog`（Vant），后台用 `ElMessage` / `ElMessageBox`；错误统一在 `client.ts` 处理，页面只处理需要特殊提示的错误码。
7. **颜色和尺寸只用 tokens**：`.vue` 和 `.less` 文件中禁止出现 `#xxxxxx` 颜色字面量（`tokens.css` 除外），由 `scripts/check-no-hex.sh` 检查；UnoCSS 禁止写任意值颜色（如 `text-[#123456]`）。
8. **访客页不能加载员工端代码**：路由全部懒加载；`pages/card`、`pages/chat` 不得 import `components/staff` 或 `pages/staff` 下的任何东西。构建后检查访客首屏资源 ≤ 300KB（gzip 前的 JS + CSS 合计按原型首屏统计）。
9. **环境判断只在 `platform/`**：页面里禁止出现 `navigator.userAgent`、`MicroMessenger` 字样，统一调用 `platform.isWechat()`、`platform.saveContact()` 等。
10. **路由守卫**：`/staff/**`（除 login）需要员工 token，未登录跳 `/staff/login`；访客页无需登录，进入时调用 `visitor/init`。
11. **Mock 只在后端接口未完成时用**，Mock 数据的类型必须来自 `api/generated`；对应接口完成后删除该 Mock 文件。
12. **页面标题**：A1 为“{姓名}｜{职位}｜数科”；员工端为“(未读数) 数科名片”，由 `usePageTitle` 统一设置。

## 6. 接口契约与通用约定

### 6.1 契约流程（防止前后端各写各的）

```text
① 后端在 modules/<模块>/schemas.py 定义请求/响应模型，在 router.py 写好路由签名（response_model 必填）
② 运行 scripts/gen-api.sh：
     uv run python -m app.export_openapi > contracts/openapi.json
     apps/h5、apps/admin 分别执行 pnpm gen:api，生成 src/api/generated
③ openapi.json 和 generated 目录一起提交
④ 前端只调用生成的函数；后端改了字段 → 重新生成 → 前端编译直接报错，不会悄悄出错
⑤ 检查脚本会重新生成一次并 git diff，有差异即失败（说明有人改了接口没重新生成，或手改了 generated）
```

前端生成工具：**`@hey-api/openapi-ts`**（生成类型 + 调用函数，使用 axios 客户端，接入 `api/client.ts` 的拦截器）。版本在 M1 锁定。

**并行开发时的“契约先行”**：如果前端要先开工，后端智能体先单独提交一个只有 `schemas.py` + 路由签名的 PR（函数体 `raise NotImplementedError`，全局异常处理返回 501），合并后前端即可生成类型、用 Mock 开发。上线前检查脚本会扫描 `NotImplementedError`，有残留不能发版。

### 6.2 路径与命名

- 前缀 `/api/v1`；分组 `/public`（访客）、`/auth`、`/me`（员工）、`/admin`（管理员），与方案第 9 章一致。
- JSON 字段一律 `snake_case`（前后端都不做大小写转换，生成的 TS 类型也是 snake_case）。
- 每个路由必须写 `operation_id`，格式 `{模块}_{动作}`，如 `card_get_public`、`lead_update_status`，它决定前端生成的函数名，**不允许用默认值**（默认值又长又会变）。

### 6.3 返回结构

- **成功：直接返回数据**，不包 `{code, data, msg}` 外壳；用 HTTP 状态码表达结果（200 / 201 / 204）。
- **分页**：统一 `Page[T]` = `{ "items": [...], "total": 123, "page": 1, "size": 20 }`，请求参数 `page`（从 1 开始）、`size`（默认 20，最大 100）。
- **时间**：数据库存 UTC；接口返回带时区的 ISO 8601（`2026-11-14T02:32:00Z`）；前端用 dayjs 按 Asia/Shanghai 显示。
- **ID**：内部用自增 BIGINT；对外暴露的名片标识只用 `card_code`；访客用 `anon_id`（UUID）。

### 6.4 错误处理

所有业务错误抛 `AppError(code, http_status, message)`，全局处理器统一输出：

```json
{ "code": "LEAD_NOT_FOUND", "message": "线索不存在或已被转交", "detail": null }
```

- `code` 在 `core/errors.py` 集中注册（大写下划线），新增错误码必须登记，前端按 `code` 决定提示。
- 422（参数校验失败）保留 FastAPI 默认结构，前端 `client.ts` 统一转换成“请检查 XX”。
- 500 只返回 `{"code":"INTERNAL_ERROR","message":"服务开小差了，请稍后再试"}`，详细错误只写日志，带请求 ID。
- 前端 `client.ts`：401 → 清 token 跳登录（员工端）或重新 `visitor/init`（访客端）；网络错误 → Toast“网络不太好，请稍后重试”；其余按 `message` 提示。

### 6.5 鉴权

| 身份 | 方式 | 有效期 | 依赖注入 |
|---|---|---|---|
| 访客 | `visitor/init` 签发 JWT（含 anon_id） | 365 天 | `get_visitor` |
| 员工 | 手机号 + 密码登录，JWT | 30 天 | `get_current_staff` |
| 管理员 | 账号密码登录，JWT（role=admin） | 12 小时 | `get_current_admin` |

请求头统一 `Authorization: Bearer <token>`。**数据隔离**：所有 `/me/**` 接口在 service/repo 层必须以 `current_staff.id` 作为查询条件，禁止从请求参数里取员工 ID；每个 `/me` 接口都要有“访问别人的数据返回 404”的测试。

## 7. 关键实现要点（智能体最容易写错的地方）

### 7.1 SSE 流式对话

- 后端用 `StreamingResponse(media_type="text/event-stream")`，响应头加 `Cache-Control: no-cache`、`X-Accel-Buffering: no`。
- **流式生成器里自己开数据库会话**（`async with SessionLocal() as db:`），不要使用路由依赖注入的 `db`：依赖注入的会话可能在流开始后就被关闭。
- 每产出一段检查 `await request.is_disconnected()`，访客关掉页面就停止调用大模型，已生成的内容照常落库。
- `<<NOKB>>` 标记的缓冲过滤见方案 7.3；这段逻辑放在 `modules/chat/stream_filter.py`，必须有“标记被拆成两段”的单元测试。
- nginx 对 `/api/v1/public/chat/` 和 `/api/v1/me/test-chat/` 关闭缓冲：`proxy_buffering off; proxy_read_timeout 120s;`，否则用户会看到回答“一次性蹦出来”。
- 前端 `api/sse.ts` 用 `fetch` + `ReadableStream` 解析（需要 POST，不能用 EventSource）；按 `\n\n` 切分事件，处理半包；支持 `AbortController` 取消。

### 7.2 大模型调用

- 业务代码只依赖 `integrations/llm` 的 `LLMClient` 接口：`chat_stream()`、`chat()`、`supports_tools()`。
- `OpenAICompatClient`：主模型 GPT、备用 DeepSeek，模型名、`base_url`、`api_key` 从 `setting` 表读取（后台可改、无需重启，带 60 秒缓存）。
- 超时：首字 15 秒、总时长 60 秒；主模型失败自动切备用，重试 1 次；记录 tokens、耗时、实际模型。
- **测试一律用 `FakeLLMClient`**（可预设回复和流式分片），CI 中不调用真实大模型；真实模型只在知识库评测脚本里用（手动运行）。

### 7.3 知识库文件

- `kb/` 目录挂载在 `/data/kb`，只能通过 `app/kb/store.py` 读写。
- 写文件用 `filelock`（按名片加锁），因为生产有 2 个 worker，`asyncio.Lock` 管不到另一个进程。
- 每次写入后在 `kb/` 目录执行一次 `git add` + `git commit`（同样在锁内），用于历史和回滚。
- 索引缓存按文件 sha1 失效，不按时间。
- `kb/` 引擎必须是纯函数为主、可脱离 FastAPI 单测；方案 6.7 的评测脚本放 `server/app/kb/eval_cli.py`。

### 7.4 同步库与阻塞

- pymupdf、python-docx、Pillow、bcrypt、git 命令都是同步/阻塞操作，在异步路由里必须用 `await run_in_threadpool(...)`（或 `anyio.to_thread.run_sync`）调用。
- 禁止在异步代码里用 `requests`、`time.sleep`。

### 7.5 定时任务

- APScheduler 只在独立的 `scheduler` 容器里运行（1 个实例），**不要在 FastAPI 启动事件里启动调度器**：api 有 2 个 worker，会导致每日汇总发两遍。
- 任务：会话结束检测与摘要（每分钟）、每日 9:00 汇总站内信、每日清理（调试会话 7 天、站内信 90 天、访客数据 180 天）。

### 7.6 限流

- 不引入 Redis。用 MySQL 计数表 `rate_counter(key, window, count)` + `INSERT ... ON DUPLICATE KEY UPDATE`，实现访客 / 名片 / 全局三级限额（方案 6.5）。
- nginx 层再加按 IP 的 `limit_req`。

### 7.7 文件存储

- 职业照、微信二维码、海报存 `/data/uploads`，通过 `integrations/storage` 的接口读写，nginx 以 `/files/` 对外提供；上传时校验类型（jpg/png/webp）和大小（≤ 5MB），文件名用 UUID，不用原文件名。

## 9. 开发顺序与任务拆分

方案第 12 章的里程碑仍然有效，这里规定的是**多智能体的执行顺序**。核心原则：**先由一个智能体做出“能跑通一条完整链路的骨架”，你确认后再并行。** 骨架阶段决定了所有后续代码的写法，并行太早会出现五种写法。

### 阶段 0：骨架（单个智能体，串行，约 3–4 天）

| 编号 | 任务 | 验收 |
|---|---|---|
| S-1 | 建仓库结构（第 4 章）、放入四份文档、AGENTS.md、CLAUDE.md | 目录与第 4 章一致 |
| S-2 | 后端：uv 项目、core/ 全部模块、Alembic、日志、错误处理、健康检查、`export_openapi`；docker-compose.dev | `uv run pytest` 通过；`/api/v1/health` 返回 200 |
| S-3 | 前端 H5：按 2.1 节改造模板；接入 tokens 与 Vant 主题；`client.ts`、`sse.ts`、`platform/` 空实现 | `pnpm lint`、`pnpm typecheck`、`pnpm build` 通过 |
| S-4 | 后台：按 2.2 节改造模板；静态路由；登录页接通后端 | 能登录进入空白首页 |
| S-5 | 契约流水线：`gen-api.sh`、`check.sh`、`check-no-hex.sh`、pre-commit（含 gitleaks 密钥扫描） | 故意手改 generated 后 `check.sh` 失败 |
| S-6 | **一条纵向样板链路**：company + employee + card 三张表 → `GET /public/cards/{code}` → A1 名片首页（真实数据渲染头图、姓名、AI 分身卡、联系方式） | 浏览器打开 `/card/sk0001` 与原型 A1 视觉一致；接口、service、repo、schema、测试、前端调用全部按规范写 |

**S-6 是后续所有模块的“抄写范本”**，你需要亲自审一遍它的代码风格，满意后再进入阶段 1。

### 阶段 1：并行开发（多个智能体）

| 轨道 | 内容（对应方案任务） | 依赖 |
|---|---|---|

### 阶段 2：集成与验收

端到端测试（10.2）、真机测试（iOS Safari、安卓浏览器、微信内置浏览器，NFC 实测）、知识库评测（方案 6.7，GPT 与 DeepSeek 各一遍）、压测（50 并发对话）。

### 冲突高发点与处理

## 10. 质量门禁与测试

### 10.1 `scripts/check.sh`（交付前必须全部通过）

```text
后端：ruff check、ruff format --check、mypy（严格模式）、pytest（含覆盖率）
契约：gen-api.sh 后 git diff --exit-code contracts/ apps/*/src/api/generated/
```

**禁止残留检查**（grep，有命中即失败）：`TODO`/`FIXME` 未附任务编号、`NotImplementedError`（发版前）、`print(`（后端用 logger）、`console.log`（前端）、`# type: ignore` / `@ts-ignore` / `as any`、`except Exception: pass`、真实手机号格式的写死字符串（测试数据用 `138 0000 xxxx` 段除外）。

### 10.2 测试分层

| 层 | 工具 | 要求 |
|---|---|---|
| 后端单元测试 | pytest | kb/、stream_filter、lead_detector、限流、权限依赖必须覆盖；`kb/` 与 `modules/chat` 覆盖率 ≥ 80% |
| 后端接口测试 | pytest + httpx.AsyncClient + **真实 MySQL**（docker） | 每个接口至少：正常、参数错误、未登录、越权（访问他人数据） |
| 验收测试 | `server/tests/acceptance/` | 按方案业务规则编写（如“调试会话不进入客户列表”“同一访客 24 小时重复留资只更新”），**由你或测试智能体编写，实现智能体只能让它通过，不能修改它** |
| 前端单元测试 | Vitest | `sse.ts` 半包解析、手机号脱敏、`platform` 判断 |
| 端到端测试 | Playwright（390×844 视口） | 访客：打开名片 → 对话 → 留资 → 员工收到站内信 → 标记已联系；员工：登录 → 改名片 → 访客端可见；每次产出截图供人工对比原型 |
| 知识库评测 | `kb/eval_cli.py`（真实模型） | 手动运行，不进 CI；验收线见方案 6.7 |

### 10.3 测试防作弊

- 实现智能体不得修改 `tests/acceptance/` 和已有测试的断言来让测试通过；确需修改要在任务卡里说明原因，由你确认。
- 禁止为了通过测试而 mock 被测对象本身；只允许替换外部依赖（LLM、文件存储、时间）。
- 测试名用中文描述业务规则，例如 `test_调试会话不计入访客统计`，方便你直接读懂测了什么。

## 11. Vibe Coding 避坑清单

### 11.1 常见的坑与对策

| # | 坑 | 典型表现 | 本方案的对策 | 自动拦截 |
|---|---|---|---|---|
| 1 | 用过时写法 | 混用 Pydantic v1、SQLAlchemy 1.x、Vant 2 的 API；代码能跑但随时出问题 | 锁定大版本 + 11.2 禁用写法表 | ruff 规则 + grep |
| 2 | 编造或随手加依赖 | 引入不存在的包、为一个小功能装一个大库、装第二个 UI 库 | 依赖白名单（第 2、3 章）；新增依赖必须写 ADR 说明理由 | 锁文件变更需人工审 |
| 3 | 接口漂移 | 前端按旧字段写，后端改了名，页面静默显示空白 | OpenAPI 契约 + 生成代码（6.1） | `check.sh` 的契约 diff |
| 4 | 重复造轮子 | 三套请求封装、两个手机号脱敏函数、四种 Toast 写法 | “唯一入口”规则（5.2）；新增工具函数前先全仓搜索 | 代码审查清单 |
| 5 | 假实现、假数据 | 函数体 `pass`、返回写死的示例数据、Mock 留到生产 | 禁止残留检查；Mock 删除规则 | `check.sh` grep |
| 6 | 测试作弊 | 改断言让测试通过、mock 掉被测对象、只测“能调用” | 验收测试锁定（10.3）；接口测试必须含越权用例 | 审查 diff 中的测试改动 |
| 7 | 吞掉异常 | `except Exception: pass`，出错时页面无反应、日志无记录 | 统一 AppError；未知异常交给全局处理器 | ruff `BLE001`、`S110` |
| 8 | 密钥硬编码 | API Key、数据库密码写进代码或示例配置 | 全部走环境变量和 `setting` 表 | gitleaks |
| 9 | 数据越权 | 员工改 URL 里的 ID 就能看别人的客户 | `/me` 只用 `current_staff.id`（6.5） | 每个 `/me` 接口的越权测试 |
| 10 | 一次改太多 | 一个任务改了 40 个文件，顺手“优化”了无关代码 | 任务卡限定可修改目录；单次提交（不含生成文件）≤ 600 行 | 审查时看文件列表 |
| 11 | 偏离方案 | 自作主张加功能、改交互、换技术 | 任务卡写明依据章节；偏离必须先写 ADR 并经你确认 | 审查清单 |
| 12 | 样式漂移 | 每个页面的蓝色都不一样，圆角各不相同 | tokens + Vant 主题变量；禁止颜色字面量 | `check-no-hex.sh` + Playwright 截图 |
| 13 | 迁移混乱 | 改已合并的迁移、两个分支各生成一个迁移导致分叉 | 9 章冲突处理规则 | `alembic heads` 只允许 1 个 |
| 14 | 异步里阻塞 | 解析 PDF 时整个服务卡住，其他访客对话停顿 | 7.4 线程池规则 | ruff `ASYNC` 规则 |
| 15 | 多进程问题 | 每日汇总发两遍；两个请求同时写同一知识文件 | 独立 scheduler 进程；filelock | 验收测试 |
| 16 | 流式输出被缓冲 | 本地正常，上线后回答一次性蹦出 | nginx 关闭缓冲（7.1） | 部署检查清单 |
| 17 | “看起来完成了” | 智能体说“已完成”，实际没跑过测试 | 完成定义（13.2）要求附命令输出和截图 | — |
| 18 | 补丁叠补丁 | 同一个 bug 来回改，越改越乱 | 同一问题连续两次修复失败，必须停下，写清现象和已尝试方法交给你 | — |
| 19 | 模板残留 | 页面标题还是 “vue3-vant-mobile”，后台残留示例菜单、Mock 登录 | 骨架任务的改造清单（2.1、2.2） | grep 模板名 |
| 20 | 时区错乱 | 线索时间差 8 小时 | 存 UTC、接口带时区、前端统一 dayjs 转换 | 接口测试断言时区 |

### 11.2 禁用写法（智能体最常犯的过时写法）

| 领域 | ❌ 禁用 | ✅ 使用 |
|---|---|---|
| Pydantic | `class Config:`、`orm_mode = True` | `model_config = ConfigDict(from_attributes=True)` |
| Pydantic | `.dict()`、`.json()`、`parse_obj()` | `.model_dump()`、`.model_dump_json()`、`model_validate()` |
| Pydantic | `@validator`、`@root_validator` | `@field_validator`、`@model_validator` |
| Pydantic | `from pydantic import BaseSettings` | `from pydantic_settings import BaseSettings` |
| SQLAlchemy | `session.query(Model)` | `await session.execute(select(Model))` / `await session.scalars(...)` |
| SQLAlchemy | `Column(Integer)`、`declarative_base()` | `id: Mapped[int] = mapped_column(primary_key=True)`、`class Base(DeclarativeBase)` |
| SQLAlchemy | 异步中访问未加载的关联属性（触发懒加载报错） | 查询时显式 `selectinload(...)`；模型关系默认 `lazy="raise"` |
| FastAPI | `@app.on_event("startup")` | `lifespan` 上下文 |
| FastAPI | 路由不写 `response_model`、返回 ORM 对象 | 必须声明 `response_model`，返回 schema |
| HTTP | `requests` | `httpx.AsyncClient` |
| 定时任务 | APScheduler 4.x 的 `AsyncScheduler` API | APScheduler 3.11 的 `AsyncIOScheduler` |
| Vue | Options API、`defineComponent({ data() {...} })` | `<script setup lang="ts">` |
| Vue | Vuex、`this.$router`、`this.$store` | Pinia、`useRouter()`、`useXxxStore()` |
| Vant | `Toast('...')`、`Dialog.confirm()`（Vant 2/3） | `showToast()`、`showConfirmDialog()`（Vant 4） |
| H5 路由 | 在 H5 里手写 routes 数组 | 文件路由（`src/pages` 目录即路由） |
| 样式 | 行内 `style="color:#2F6BFF"`、写死 px 颜色 | tokens 变量 / UnoCSS 主题类 |

## 12. 智能体强制规则（AGENTS.md 来源）

> 以下内容已单独生成为 `repo-init/AGENTS.md`，放进代码仓库根目录即可。所有智能体每次开工前必须读它。

1. 开工前先读：`AGENTS.md`、任务卡、任务卡引用的方案章节和原型页面。不清楚就停下来问，不要猜。
2. 只改任务卡允许修改的目录；发现必须改其他地方时，停下并在交付说明里提出。
3. 不得偏离四份文档；确需偏离，先在 `docs/adr/` 写一条决策记录，并等待确认。
4. 不得新增依赖，除非任务卡允许或已有 ADR。
5. 接口改动必须走契约流程（改 schema → 运行 `scripts/gen-api.sh` → 提交生成结果）；禁止手改 `contracts/` 和 `src/api/generated/`。
6. 遵守 11.2 禁用写法表；拿不准某个库的当前 API 时，查该库在锁文件中对应版本的官方文档，不凭记忆写。
7. 禁止编造公司业务内容；示例数据只用 `kb-test/` 和测试夹具里的内容。
8. 禁止硬编码密钥、域名、模型名；全部从配置读取。
9. 不得修改 `tests/acceptance/`；不得通过修改断言或 mock 被测对象来让测试通过。
10. 同一问题连续两次修复失败，停止修改，写清现象、已尝试的方法和怀疑的原因。
11. 交付前运行 `scripts/check.sh` 并全部通过；前端任务附 390×844 截图，与原型对应页面并排对比。
12. 交付说明按 13.3 的格式写；不要声称“已完成”而不附检查结果。

## 13. 任务卡、完成定义与审查清单

### 13.1 任务卡模板（你或调度智能体分派任务时使用）

```markdown
## 任务 {编号}：{标题}

- 轨道：后端·业务 / 后端·知识库与对话 / 前端·访客 / 前端·员工端 / 前端·后台
- 依据：开发方案 §{章节}；UI 规范 §5 {页面编号}；原型 {页面编号/状态}
- 目标：{一句话说明做完后用户能做什么}
- 允许修改：{目录列表，例如 server/app/modules/lead/、server/tests/api/test_lead.py}
- 不得修改：core/、tests/acceptance/、其他模块
- 接口：{涉及的 operation_id 列表；是否需要先提交契约 PR}
- 数据库：{是否需要迁移；涉及的表}
- 验收标准：
  1. {可验证的行为，例如“员工 A 请求员工 B 的线索返回 404”}
  2. ...
- 必须通过：scripts/check.sh；{额外命令，如 pytest tests/acceptance/test_lead.py}
- 交付物：代码 + 测试 + {截图 / 接口示例}
```

### 13.2 完成定义（Definition of Done）

- [ ] 验收标准逐条满足，并在交付说明中逐条对应
- [ ] `scripts/check.sh` 全部通过（附输出末尾）
- [ ] 新增/修改的接口有接口测试（含越权用例）；新增业务规则有单元测试
- [ ] 契约已重新生成并提交
- [ ] 前端页面附截图，与原型一致；空状态、加载态、错误态都有处理
- [ ] 无禁止残留（TODO 无编号、console.log、print、any 等）
- [ ] 没有修改任务范围外的文件
- [ ] 如有偏离方案之处，已写 ADR

### 13.3 交付说明格式

```markdown
## 任务 {编号} 交付说明
- 完成内容：{逐条对应验收标准}
- 修改文件：{列表}
- 数据库迁移：{文件名 / 无}
- 接口变更：{operation_id 列表 / 无}
- 检查结果：{check.sh 输出末尾}
- 截图：{路径}
- 未完成 / 风险 / 需要确认：{如实写，没有就写“无”}
```

### 13.4 审查清单（审查智能体或你使用）

1. 改动是否只在允许的目录内？有没有“顺手优化”的无关改动？
2. 是否有 11.2 中的禁用写法？
3. 路由是否瘦（无业务逻辑、不直接查库）？service 是否 import 了 fastapi？
4. `/me` 接口是否只用 `current_staff.id`？越权测试是否存在且有效？
5. 新增错误码是否登记？异常是否被吞掉？
6. 异步代码里有没有阻塞调用？
7. 测试是否真的验证了业务规则，而不是只验证“返回 200”？测试断言有没有被放宽？
8. 前端是否直接写了 URL / axios / 颜色字面量 / `any`？是否引用了另一端的组件？
9. 页面与原型对比：布局、文案、颜色、状态是否一致？
10. 有没有新增依赖？有没有 ADR？
