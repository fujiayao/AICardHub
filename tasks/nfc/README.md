## 3. Magpie 与执行器职责

Magpie 管模型路由；Codex CLI、Claude Code 等执行器负责目录、工具、进程和会话。总控负责派工、依赖、集成与回收。`magpie <agent> <model>` 不能当作启动任务命令；不使用不存在的 `/tasks` API。

本轮只读探测 `http://127.0.0.1:3425/v1/models` 返回 200 和 12 条模型 ID。核对了本机 `codex exec --help`、`claude --help`。尚未做本轮模型生成/工具闭环；目录中的模型不等于可成功完成开发。旧 DeepSeek Harness 故障记录留在 `docs/开发执行器使用.md`，不得当作新路由已失败或已修复的证据。

建议角色与本机已列出的候选模型：

| --- | --- | --- |
| 总控/集成 | `gptpro/gpt-6.1-sol` | 冻结契约、派工、合并、裁决；失败换已验证 GPT 路由 |
| 后端与契约 | `gptpro/gpt-6.1-sol` | 短链、接口、测试和唯一 OpenAPI 导出者 |

### 启动前检查

1. 读取项目 AGENTS、相关子目录规则及批准 ADR；核对本次文件/接口所有者。
2. 核对 CLI help、Magpie 模型列表和进程级 provider/profile，确认请求确实走本机 Magpie。不要只传 `-m` 就宣称经过 Magpie。
3. 每种拟用执行器/路由先在独立 scratch 做合成任务：写一个标记文件、读回、报告结果；记录模型、协议、工具事件、耗时和退出状态。审查角色只验证读取。
4. 优先用 Codex CLI 的 Responses 或 Claude Code 的 Messages 已验证入口；不要把 Chat Completions 文字成功当作 agent 工具循环成功。凭据由本机配置或环境引用，不入提示词/日志/Git。
5. 合成闭环连续两次同原因失败，切到已验证路由，保留失败证据；只终止本次创建的进程。依赖或硬件等待列出可继续任务，不空等。

下面仅是 help 已核对的执行形态，不是已配置好的 Magpie 连接，也不会自动启动任务：

```powershell
# $taskWorktree、$promptFile、$modelId 由总控从本轮已验证派工记录填入。
# 先确认当前执行器 provider/profile 已指向 Magpie。
Get-Content -LiteralPath $promptFile -Raw | codex exec -C $taskWorktree -m $modelId -s workspace-write -
```

审查任务换为只读运行；实际环境不支持该权限模式时选择平台支持的等价隔离，不能无声改成无限权限。后台 Windows 进程用隐藏窗口，保存 PID 和输出位置；任务正文通过文件/标准输入交付，不拼成动态 shell 命令。执行器若有 approval 等待，由总控定位到具体动作处理，不以无限权限绕过。

## 4. 角色所有权与并发

默认总并发最多 4：一个总控 + 最多三个 worker。先单路验证，再逐步扩大；429、上下文失败或资源不足时减少并发。同一时刻每个可写文件只有一个所有者。

| 任务 | 所有者 | 工作区/分支建议 | 主要允许范围 |
| --- | --- | --- | --- |
| NFC-00 | 总控 + 安卓角色 | `feat/nfc-android` | 原型及构建输入；总控记录冻结信息 |
| NFC-01 | 后端 | `feat/nfc-backend` | workspace 路由/schema/分享逻辑及对应 tests；唯一导出 contracts |
| NFC-02 | H5 | `feat/nfc-h5` | 员工分享页、`pages/share/nfc.vue`、platform、路径工具及本端 tests |
| NFC-03、06 | 同一安卓角色 | `feat/nfc-android` | `apps/nfc-android/`，共享 Manifest/Gradle/模式控制器不并发编辑 |
| NFC-04A | 后台 | `feat/nfc-admin` | Scope 和必要菜单/发布信息展示 |

总控使用独立集成工作区，主工作区保持其他进行中任务的改动。创建 worktree 前先查有没有合适的已有工作区。每个派工记录实际路径、基线提交、允许文件、模型、前置交付提交和契约 hash；预设分支名已存在时复用或加明确后缀，不覆盖。

## 5. 波次与交付门槛

### 波次 A：冻结与原型

总控冻结 URL、App Link、依赖和任务所有权（见角色任务卡共享契约）。三个 worker 可分别做：安卓原型、后端轻量接口、QA 用例设计。原型先验证两台安卓，再安卓→iPhone；样品未到时仍可完成贴纸逻辑和单元测试。

完成标准：基线记录、公开短链/导入参数约定、后端新 OpenAPI、安卓可构建原型、明确哪些设备结果已测/待测。硬件未到不阻止波次 B，但不得关闭硬件门槛。

### 波次 B：主要实现

后端契约完成并集成后，三 worker 为安卓、H5、后台。安卓在单一分支顺序完成 NFC-03 与 NFC-06。H5 从真实 OpenAPI 生成客户端。后台可以先按能力状态编写说明，再填真实 APK 版本。总控准备安装与发布配置。

完成标准：短链导入、手机模拟、读取、写贴纸、回读、模式切换、H5入口都存在；自动检查结果和候选 APK 可交付。不得将 mock 的原生能力报告为真机通过。

### 波次 C：集成、独立 QA、修复

按后端 → 安卓 → H5 → 后台顺序集成指定提交；每步检查影响范围，避免一把合并所有分支。三个 worker 可做 QA、独立审查、被派发的修复；修复权明确交还原所有者。关键复核输入为已集成提交 diff 与报告，不能只评估原始方案。

软件检查、APK 构建、手机射频、贴纸射频、线上部署五种状态单独记录。未采购贴纸时可交付“软件候选 + 待验硬件清单”，不宣称贴纸功能最终验收。

### 波次 D：有样品后的验收与发布候选

按贴纸规范进行采购样品验证和抽检，修复后复测失败组合。总控生成发布候选与回退步骤，确认域名根关联文件不会影响原网站。采购、不可逆锁卡、生产发布不属于自动派工默认动作，另按用户实际授权执行；本期代码不提供永久锁卡功能。

## 6. 调度纪律

- 工作状态：`ready / running / awaiting_dependency / awaiting_hardware / review / changes_requested / software_done / accepted`。软件完成与硬件未验可同时记录；只有全部必需门槛通过才 accepted。
- worker 一次只领一个任务或明确允许的连续任务组。失败反馈写“现象、证据、两次尝试、下一定位点”，不反复生成同一修复。
- 报告写本角色独立文件；仅总控汇总，不让多个 worker 共写一个看板。
- 文档与源码使用项目允许的上下文；不要把员工库、供应商凭据和私有知识打包进审查提示词。
- 新依赖仅限经总控记录的 Android 构建和 UI 最小依赖；保持现有 Web/后端栈。数据库迁移不是本期默认工作。
- 发布前重新读取名片/活动状态；公开内容与已有留资/会话隔离规则保持。
